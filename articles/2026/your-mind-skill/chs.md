# Skill 如何工作

在了解该如何提升 AI 的效率，我们需要先了解一些背景基础知识，正所谓知其所以然才能更好驾驭。但限于篇幅，以及相比大家对 AI 的了解程度已经很深，所以我们直接从本优化内容最接近的 Skills 开始说起。

## 工作流

Skills 让我们能够以简洁直观的手段驱动 AI 完成复杂的任务，甚至是一些需要专业技巧的工程化任务。那么这是怎么做到的呢？

通过诸如 Codex 等工具，我们将我们的想法，用自然语言描述的方式写入进去。大语言模型结合内置的和已注入的 Skills，形成一套能够执行的基础方案，其中包括任务的拆解和关注度的控制，以及对各项工具和 Skills 可能的运用。随后自动化执行，执行的过程实际仍然会有所思考和调整。最终得出结果。名副其实的智能助理。

## 为工具准备

LLM 只拥有对文本的理解和处理能力，以及内置了海量知识储备。文本通常基于语言描述，不同语言对于 LLM 来说，都可以在训练过程中逐渐掌握，这其中包括人们常说的英文和中文。LLM 擅长 Markdown 表述内容，也缘于在训练时基于此种方式学习，所以，在 LLM 的视角看来，Markdown 就是语言表达本身的一部分。除此之外，此前 LLM 的训练曾被针对 JSON 格式进行了调优增强，而之所以要做这件事，是为了实现一项对后续 LLM 发展有着重大影响的功能：工具调用。

JSON 在计算机世界里，经常充当数据传输的职责。当我们让 LLM 按照一个指定的 JSON 格式输出一组结构化数据，使得这些数据能够被预先准备好的 API 读取，从而让 AI 在处理或获得一些不太了解的信息时，能够调用外部程序来完成，而程序返回的 JSON 格式结果，又重新被 LLM 读取和解析，从而继续走完后续 AI 流程。这便是工具调用。为了支持更多工具，LLM 输出的 JSON 通常会包含需要调用工具的名称或标识，以及这个工具（也就是 API）所需要的参数；而工具返回的 JSON 内容，会附加在 Prompt 上，连同原始的上下文，重新交给 LLM 继续执行。

## AI 工具

AI 工具在历史的发展中也经历了多个阶段，从早期的插件机制，到后来的 Function Call，再到更适合分发的 MCP Tool，又到现在流行的 AI Skills，这中间可能还有一些中间态和分支，但时至今日，这些 AI 工具中的许多历史形态，通过一层调一层的方式，其实仍然是构成 AI 任务执行的一部分，而并不是简单地被淘汰，例如 Skill 底层会调用 MCP Tools 和 Function Call，因此都是存在的，只是被逐层进行封装。

而任务的编排能力，也是 AI 一路发展过程中，不断强化的一项基础隐藏技能。因为，当任务在工作链路、引用资源和上下文关联等方面上都非常复杂时，良好的编排能力能节省许多多余的步骤，从而尽可能不走弯路，并且无论是站在宏观角度还是微观角度上，都更好地理解相应流程上的职责和目标，从而提升整体的效率。

## 工作原理

LLM 根据用户描述的任务判断目标和工作方向；随后根据已注册（包括内置）Skill 的名称和概述，选择合适的 Skill，并在需要时读取其具体内容。之后，LLM 按照 Skill 的内容执行相应步骤，并根据返回的结果重新组织回复。很多时候，一个任务会使用多个 Skill，或多次使用同一 Skill。

具体的 Skill 描述了更详细的执行事项。这些事项通常包括对具体工具的调用，例如 MCP Tools 或内置的 Function Call 接口，用于执行命令、访问网络或操作文件等。Skill 也会说明这些工具的调用方式及所需参数。多数情况下，参数采用 JSON 格式，但并不绝对。

# 提升空间

通过一系列技巧和技术，我们可以在复杂的 AI 场景中，大幅提升其工作效率。

## 调优方向

经过对 Skill 模式的运作方式了解，我们知道了 AI 会对先对任务进行编排，然后调用具体工具，并最终以整个自动化工作流的方式完成。因此，我们也就针对这3个方向，进行定向调优，形成一套切实可行的 Skill，能以更优良的方式运作。

## 适用范围

所谓复杂 AI 场景，指的是以下几个方面：

- 处理链路较长，拥有多个重要步骤，环环相扣，甚至可能还有一些分支，以及会涉及对 LLM 的多次访问。
- 拥有多层外部数据引用，并且这些数据之间可能还会存在关联，即先要获取一组数据，然后用这组数据里的一些信息，进一步获取下一组数据。
- 稳定且可复用的流程，也就是说这套新搭建的 AI 场景，是会在后续被频繁用到的。

下面介绍的这一组 Skill，即是为此而生。其它场景或许不能完全用上，但里面的一些想法获取可以被借鉴。

## 示例

为了便于说明，这里将贯穿一个真实案例，即面向相关负责人推送的每周招聘数据汇总情况。这个周度简报通过办公 IM 推送，里面包含了一句话概览、近一周面试统计、入职推进统计、重点岗位概览，然后会有个指向完整报告的链接。除此之外，这个服务其实还只是一个更宏大的智能招聘服务系统中的一部分，而该招聘服务则还包含了更多相关能力的 AI 服务。

那么简单说来，在这里，这涉及到了数据统计、状态分析、通知、系统服务整合。

## 聊天就能实现

要完成这样一个服务，我们可以打开 Codex，输入以下提示词。

> 生成一个飞书卡片并发送给我，里面汇总近一周内的面试、Offer 沟通、入职相关数据，以及关键岗位概览。

似乎描述的很清晰，接下来就静待其执行，看看效果如何，不好再改。

但是，这么做很简单，但这不是最优解。前面提到过，我们在 AI 时代，坐享 AI 成果，然而这不仅是一种可以达成的顺利风向，也还是一种需要重新思索和适应的新挑战，我们依然需要鼓起勇气，拿出学习精神，想尽办法来更充分利用好 AI。

# 提示词工程

首先，这里要先要介绍第一个被认为是 Solid 的 Soft Skill，叫做提示词工程（Prompt Engineering）。

Solid 和 Soft 似乎在某个层面上是组反义词，但大家应该都知道 Prompt Engineering 的重要性，所以这个 Soft Skill 的确很 Solid。AI Prompt Engineering 是面向 AI 提示词的针对性调优，效果很显著，尤其在 LLM 发展的早期非常被人看重，随着 LLM 智能化的增强，这一块逐渐被人们淡忘，但越是在高要求、高标准、高追去的项目中，也就是所谓的高杠杆 AI 场景中，需要更深入有效地推进，我们就越是要在这一领域充分进行深挖。

## 指引

我们可以在网上搜到许多 Prompt Engineering 方面的知识，其中会包含许多值得关注的点。这里也列举了几点，后面会详细介绍。

- 明确目标与输出规范
- 适当的上下文与背景信息
- 数据准备与输入规范
- 清晰的任务指令与边界情况处理

## 明确目标与输出规范

我们需要明确的说明 AI 任务需要完成的具体目标，并定义预期输出的结构、语气、篇幅、格式及详细程度，这样才能获得想要的结果。

例如，刚才的招聘周度简报示例里，可以清晰地明确目标和输出规范。

> 生成一个飞书卡片并发送给我，里面包含以下区块。
> - 一句话概览。
> - 本周面试：展示面试轮次、人数、未通过、含 AI 评估的数量，并分别按上面数字、下面标签的块状结构展示。
> - 入职推进：用一个表格呈现统计数据，包含列有本周和整体，行为 Offer 沟通、待入职、新入职。
> - 关键岗位：用 3-5 行列表形式，简述关键岗位的面试和入职情况。

像这里面，目标、结构（小标题和描述）、内容长度、格式，都做了清晰的定义，AI 在按照指定结果输出，那么就很容易符合我们的预期。

## 适当的上下文与背景信息

需要提供必要的业务背景、用户场景及相关其它信息，让 AI 更加精准快速明白自己此轮任务的目标和结果。

例如刚才的示例，我还会告诉 AI 各入职推进状态的具体定义是什么，本周的范围是什么，确保这些可能村子不同解释的关键指标是理解一致的，这样不容易出现后期校验时发现口径不一致的问题，争取降低返工频率和次数。

## 数据准备与输入规范

通过将所需要引用到的输入信息，准确地进行描述，来提升 AI 对数据使用的准确度和可靠性，包括说明需要用到什么数据，从哪获得为宜，数据之间的关联是什么，以及数据结构中隐藏的信息。

很多时候，AI 会自己判断、自行寻找、自动整合，但你对场景实现的上游情况了解，提供清晰的数据源描述，会对 AI 产生很有利的帮助，就像你被指派任务时，如果有人能提供一份类似清单，并且里面的内容是准确有效的，相信你也能在处理时高效不少。

例如上例中，招聘信息其实并不是很好找。在系统中，信息被按层级和类型，打散在多出，并且有多个层级和平行关系，导致对一个直观上简要的信息查找，需要经过多个 API 的获取。例如，要查某个人员的面试时间和工作岗位，需要先查询人才库，定位该面试者，在根据其 ID 找到他的投递信息，而这里面会关联工作岗位，但只有 ID 没有其它信息，于是拿着该 ID 去工作岗位信息里去找到他正面试的岗位名称，同时还要在面试记录里，用招聘 ID 去筛选出哪些面试安排是该应聘者的，并依次找到面试时间。一连多个数据源查询，只是出来了这样一条记录。这些信息，尤其是数据的结构、数据间的关联、数据用途，将其描述清楚交给 AI，那么就能非常快且准地稳定完成任务，而具体的查询方式则可大胆放心交给 AI 自行编排。

## 清晰的任务指令与边界情况处理

很多时候，我们制定的任务会比较复杂，因此对任务的一个上层拆解也很重要，确保每个步骤都是可执行的，并对可能存在的不同分支和情形进行解释，以及对于诸如信息缺失、相互矛盾、无效或超出支持范围的边界深至易仓情况，也说明处理方式，这样才能确保在任何场合下都能给出高质量的结果。

例如上例中以下几个场景可以作为参考。

- 步骤拆解：将提供统计信息这一措辞，改为，先列出投递和面试信息，然后分别根据状态来进行统计。这样确保它的统计是符合我们预期的。
- 边界处理：新入职的完整数量统计留空，因为这是没有意义的信息；如果当周新入职为空，那么这一整行数据都去除。通过这样一段表述，可以清晰地让 AI 知道如何处理新入职统计的特殊情况，而不是根据它的心情自由发挥。
- 定义明确：关键岗位的定义是满足后续 3 条中的一项，1 近期拥有较多面试量，2 职级较高，3 与业务强相关；同时，将工作职责一致的岗位进行合并统计。这可以让 AI 明白，关键岗位这一带有非常主观色彩的词汇，究竟是何意，确保后续判断尽可能符合预期。

# 预备数据

除了对提示词进行优化外，我们还可以对我们的 AI 服务所需要读取的数据进行预先整理，因为你会发现 AI 的许多深度思考步骤，都是和数据获取有关的，但如果我们有渠道能提前获取好这批数据，那效率显然也会得到提升。接下来我要介绍的被认为是 Premium 高级 Soft Skill 的，叫做 预备数据。

## 数据访问

通常来说，我们的外部数据可能多种多样，并且很复杂。通常会涉及多个 API 或其它类型数据源，而且这些数据之间会存在关联和嵌套关系，前面在说招聘示例时有说明过。但有时我们也能另辟蹊径，通过一些简单的方式提前获取到这批数据，例如制作一个报表，建立好映射关系，然后再将数据直接下载下来，发给 AI。

这样一来可以节省很多 LLM 的运行时间，包括深度思考过程中推断数据间的关联，和完成整个数据获取链路不断打断重来和分批获取的时间，因为 LLM 的每一轮工具执行，都会将内部会话暂停，等结束后拿到结果再接续这个会话，等于时内部进行了多次聊天的过程，LLM 和众多工具之间安静的对话。除此之外，词元消耗也显然得到了大幅的降低，毕竟节省了刚才说的这些中间过程，交互往返的内部聊天少了许多。

## 关键数据准备

制作报表当然只是其中一个简单的方式，还有许多其它方法，而且报表也不是适用于所有场景。

那么即便时报表，我们回到招聘的这个例子，我这边就建立了一个 招聘-面试 底表，以招聘为圆心，将候选人、岗位、员工（如果已入职）的相关信息都整合到一张多为表的数据表中，然后将面试记录整合到另一张数据表中，之后 AI 只需要读取这张表即可，而不用颠三倒四请求那么多无用的接口，并且这些数据是经过精简和额外处理过的，剔除了许多无用数据，又包含了少量经计算或映射的其它数据，因此总数据量反而比原先的少。

## 可重复适用的中间信息

事实上，对于大型服务和公共数据服务，许多预先准备的数据都是有可以被充分利用的场景的，我们可以将相关数据存储于线上，方便多个 AI 服务共同访问，因此进一步提升预备数据的利用率，提升利用率也就意味着分摊到每处的消耗更地。

针对一些访问频度较高的数据，可以采用定时更新或按策略更新的机制来维护；对于频度没那么高的，可以在其依赖项全部就绪的时候，由相关事件触发更新，从而降低预备数据所需的额外网络开销。

以上招聘相关数据是采用定时更新的模式。虽然这个周度简报看起来触发频率非常低，但这套中间数据支撑着 HR AI 系统的许多模块，也支撑着一些更上层的报表和看板，许多服务对时效性要求都较高，因此是每天数次更新。更新时显然也是采用增量更新，不会全局更新，因此网络消耗也非常低。

## 数据流

经过精简后，AI 在执行时的内部数据交流就简单多了，不用再一轮一轮调用不同 API，Agent 内部聊天轮次也跟着大幅降低。

# 重工业

重工业是指为国民经济各部门提供物质技术基础的主要生产资料的工业，其产品主要用于生产建设和基础设施领域，而非直接面向消费者生活。包括一些生产机器的机器、生产工具的工具，很多也都属于重工业。然后我要介绍的被认为是 Superior 卓越 Soft Skill 的，叫做 制造工具的工具，通过让 AI 回归 AI 本真，释放 AI 原动力。

最近 Trump 先生建议将 AI 更名为卓越智能（Superior Intelligence），就是这个卓越一词。

## Skill 模式的底层

在介绍之前，让我们再看看 Skill 模式的底层的运作方式，非常有趣。

如前面介绍到过，Skill 本身只是描述某一任务或子任务在执行时，其需要遵循的执行路径策略、调用的底层工具和输出约束等信息，这些都只是描述，但这个描述里，关于其所提到的具体步骤的执行，其实又是指向了另一些更底层的工具。这些工具可能又是一些 Skill，这种组合多个 Skill 的 Skill 我们通常称它为组合 Skill；还有一些是指向一些工具，这种通常称为原子 Skill，但工具本身并不一定在这个 Skill 里，工具可能是已经存在的或是通过别的 Skill 另行安装的，而这个 Skill 只是介绍这个工具该如何使用。

工具通常是个网络请求，或是个命令行程序，又或是个 MCP Tool，当然还有可能是其它内建能力。这些大多都是有标准化格式去触发的，因此描述工具调用方法的 Skill 只需描述这个工具的类型和名字，以及需要传入怎样的参数，LLM 就懂得如何触发了。

最终，LLM 通过这些嵌套的 Skill 组合，将一段表述话语，真的执行了起来。

## 发送一条评论

但这个 Skill 嵌套关系的水到底有多深呢？让我们以在飞书知识库云文档发表一条划线评论为例来说吧。

假设相关环境和配置已经全部就绪，即飞书 CLI 已安装好并配置好，要评论的文档也已准备好，即便在这么准备充足的情况下，AI Agent 会调用哪些 Skills 来完成评论操作呢？

首先，它会根据在安装飞书 CLI 时已获取的相关 Skill 信息，知道读取文档（评论前需要先知道文档的内容及包括各部件 ID 在内的内部结构才能评论）需要调用一个名为 `lark-doc` 的 Skill，里面介绍了飞书云文档的一些基础信息，同时也提及读取此 Skill 前还得先读取 `lark-shared` Skill，因此又立即通读了一遍该 Skill。随后在 `lark-doc` 中发现，对文档的具体读取是由一个名叫 `lark-doc-fetch` 的 Skill 介绍的，于是又通读一遍该 Skill。

接下来，LLM 需要了解发评论的功能了，这在 `lark-drive` Skill 中。该 Skill 的前置必读也指向了 `lark-shared` Skill，然后又提及了 `lark-drive-comment-location` 是评论定位、`lark-drive-list-comments` 是评论列举，`lark-drive-add-comment` 是添加评论这 3 各 Skills，这些都是 LLM 统统需要学习的资料。

学海无涯苦作舟。学成归来的 LLM，带着它的知识和想法，按照这些 Skill，通过内建命令执行工具，正确调用飞书 CLI 来执行，才完成了这个发送一条评论的任务。故事很励志。

## 固化工作流

发评论事小，但有许多前面提到的高杠杆场景，包括这个招聘示例，其内部流程本身就很复杂，再加上里面其实每个小点又像这个发评论一样复杂，导致事情其实是原本认为的复杂程度的平方那么多。

但其实，如果这个流程是高频的，我们可以将它固化。

回到招聘周度简报的例子，刚才我们搭建了两个数据表作为中间信息存储容器，如果这个数据表是通过多维表格内置的报表能力搭建的那么也是可行的，但如果遇到前面提到的无法用报表或现成自动化工具搭建时，我们或许还通过 AI 去搭建。但如果用 AI 搭建，除了复用能带来效率大幅增加外，其表格内容的初始和维护本身，还是和以往一样非常具有消耗性，我们需要访问多个数据源来获取信息，然后将这些信息整合在一起，最终还要存储在一个新的多维表格中。

但其实这些流程和 LLM 是可以没有关系的，因为对这些数据的获取以及整合，再到保存线上，都是可以用程序去实现的，完全无需消耗词元，或很少消耗词元，并且具有显著优异的性能和稳定性。事实上这个招聘中间信息存储就是用程序实现的。

## AI 编程

但这不是显著提高门槛了吗？怎么又要编程了呢？

不着急，打开你的 Codex 或 GitHub Copilot 或其它 AI 工具，让它帮你搞定。

你可以先按照先前的方式，将数据整理好，然后告诉 AI，将刚才的数据整合思路生成为一个程序，或者一个 Python 脚本，然后在去验证新生成的这个程序或脚本的运行情况。没问题后，写个 Skill 去运行这个脚本，让 AI 在指定的时候去触发这个 Skill 即可。

嗯，正如你所想，用 AI 开发服务于 AI 的工具，再让 AI 按预期模式执行这个 AI 工具，然后再让 AI 去读取这个 AI 工具生成的为 AI 提供的信息，最终由 AI 产生最终结果。一切就是这么圆满！

## 研发开销

这里面其实就是多了一个生成为 AI 预先准备数据的工具，但对后续能带来显著影响。

另外，如前面提到的适用场景，这套模式其实只适用于可复用的复杂模式，其它更简单的场景其实是不需要走这个“制造工具的工具”这一步的。

# 你的思想

但是，这对于其它场景仍然是具有借鉴价值的。这里说的这些，其实是想让大家意识到，为了充分挖掘 AI 的潜力，我们一方面在享受 AI 带来的便利，另一方面也需要站在当下现实中 AI 的角度去使用，才能带来显著受益，才能获得预期结果。

说到这，也许你会很纳闷，说好的能大幅提升 AI 效率的好 Skill 在哪？那么接下来就是终极大杀器：被称为 Mind 思考 Soft Skill 的，叫做你的思想，将为你所拥有。

## 全是你的

前面先是介绍 Solid Soft Skill——提示词工程，进一步到 Premium Soft Skill——预备数据，然后进阶到 Superior Soft Skill——制造工具的工具，最后来到 Mind Soft Skill——你的思考。没错，这个 Skill，其实不是给 AI 的 Skill，而是给你的 Skill，给你用来了解和深度使用 AI 的 Skill。英文 Soft Skill 其实指的是 EQ 相关的技巧，而 EQ 通常指的是人与人之间的处事关系，但我这里其实指代的是人与 AI 之间的初始关系，因此，当你通过以上这些 Soft Skill 系列抛砖引玉，更明白如何操控好 AI，这是一套方法论，也是你的思考模式，是你的 Mind Soft Skill。

## 理念

不同场景可能会有不一样的具体处理和优化方式，找到最合适的才是最关键的。通过对可复用复杂 AI 场景的效率提升方法论的介绍，希望能对大家未来使用 AI 能有所借鉴。

## 接下来

总结一下，在和 AI 交流时，请确保自己对任务的目标、输入、结果、约束、边界等都能有明确的约束，并在可能的情况下将需要的数据提前准备，甚至为 AI 工具在运行过程中的一些其实与 LLM 无关但必要的一些流程，通过 AI 实现的方式实现成一些固化工具和 Skill 代理完成，从而最终实现高效、稳定、可控，且结果质量好的 AI 服务。
